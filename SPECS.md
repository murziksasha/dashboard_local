# Dashboard Local — функціональна специфікація (v1.1)

Документ описує всі реалізовані функції програми **послідовно**: від першого запуску до адміністративних операцій.

---

## 0. Призначення та обмеження

| Параметр | Значення |
|----------|----------|
| Призначення | Локальний облік задач (аналог Jira) для команди |
| Користувачі | до ~50 одночасних |
| Розгортання | один сервер (Windows PC), доступ у LAN через браузер |
| UI-мова | українська (`uk-UA`) |
| Стек | Next.js 15 + TypeScript + SQLite (`node:sqlite`) + Tailwind |
| Дані | файл `data/dashboard.db`, вкладення `data/uploads/`, бекапи `data/backups/` |
| Порт за замовчуванням | `3000` (`0.0.0.0`) |

## 1. Перший запуск і автентифікація

### 1.1. Setup-майстер (`/setup`)

**Коли:** база ще не ініціалізована (`setup_complete ≠ 1`).

**Функції:**
1. Вказати назву інстансу.
2. Створити першого адміністратора (імʼя, логін, пароль ≥ 6 символів).
3. Опційно завантажити демо-проєкт і користувача `demo` / `demo1234`.
4. Після успіху — автоматичний вхід і перехід на `/dashboard`.

**Правила:**
- Повторний доступ до `/setup` після ініціалізації заборонено (редирект на `/login`).
- Акаунти користувачів далі створює лише Admin.

### 1.2. Вхід / вихід

| Функція | Опис |
|---------|------|
| Логін (`/login`) | Перевірка логіна + пароля (scrypt), створення cookie-сесії |
| Сесія | HTTP-only cookie `dl_session`, термін ~14 днів |
| Вихід | Видалення сесії з БД і cookie |
| Захист маршрутів | Неавторизований користувач → `/login`; незавершений setup → `/setup` |
| Ліміт спроб | 5 невдалих входів з однієї пари IP+логін за 15 хв → пауза 15 хв |
| Аудит | Успішний/невдалий вхід пишеться в `audit_events` (Адмін → Аудит) |

### 1.3. Тема оформлення

1. Світла / темна / системна.
2. Перемикач у шапці додатку.
3. Збереження вибору в `localStorage`.

## 2. Ролі та права доступу

### 2.1. Глобальні ролі

| Роль | Можливості |
|------|------------|
| **Admin** | Усі проєкти; користувачі; команди; бекапи; налаштування інстансу |
| **User** | Лише проєкти, до яких є membership (прямо або через команду) |

### 2.2. Ролі в проєкті

| Роль | Права |
|------|-------|
| **Lead (Керівник)** | Налаштування проєкту, статуси, custom fields, учасники/команди, спринти |
| **Member (Учасник)** | CRUD задач, DnD на дошці, work log, вкладення, коментарі |
| **Viewer (Спостерігач)** | Перегляд + коментарі (без редагування задач) |

**Джерела доступу до проєкту:**
1. Прямий запис у `project_members`.
2. Через `project_teams` + членство в команді.
3. Admin завжди має права рівня Lead.

## 3. Навігація та оболонка додатку

Після входу доступна оболонка:

1. **Бічна панель:** Дашборд, Проєкти, Команди; для Admin — Користувачі, Керування командами, Бекапи, Аудит, Налаштування.
2. **Шапка:** привітання, пошук (`Ctrl+K` / `/`), дзвіночок сповіщень, меню аватара (тема, щільність, профіль, вихід).
3. **Адмін у сайдбарі:** Користувачі, Керування командами, Бекапи, Аудит, Налаштування.
4. **Адаптивність:** на мобільному — кнопка меню (бургер), горизонтальний скрол дошки.

## 4. Особистий дашборд (`/dashboard`)

Віджети (усі лічильники та списки **без soft-deleted** задач):

1. Кількість моїх відкритих задач.
2. Кількість прострочених (due date < сьогодні, статус ≠ done).
3. Кількість доступних проєктів.
4. Кількість непрочитаних сповіщень.
5. Список «Призначено мені».
6. Список «Прострочені».
7. Список «Мої проєкти» (перехід у проєкт).
8. Список «Нещодавно оновлені» задачі.
9. Черга «Моя черга» (overdue / сьогодні / тиждень / в процесі / без дати).

## 5. Команди

### 5.1. Перегляд (`/teams`)

1. Список команд із кількістю учасників.
2. Для Admin — посилання на керування.

### 5.2. Керування (`/admin/teams`) — лише Admin

1. Створити команду (назва, опис, учасники).
2. Додати учасника до команди.
3. Прибрати учасника з команди.

---

## 6. Користувачі (`/admin/users`) — лише Admin

1. Створити користувача: логін, імʼя, email (опційно), пароль, роль (`user`/`admin`).
2. Увімкнути / вимкнути акаунт.
3. Скинути пароль.
4. Не можна деактивувати самого себе.

## 7. Проєкти

### 7.1. Список проєктів (`/projects`)

1. Показати проєкти, доступні поточному користувачу.
2. Admin може створити проєкт:
   - ключ (2–10 символів, `A-Z0-9`, починається з літери);
   - назва, опис;
   - автоматичні дефолтні статуси: Backlog → To Do → In Progress → Review → Done;
   - творець стає Lead.

### 7.2. Вкладки проєкту

Для кожного проєкту:

| Маршрут | Призначення |
|---------|-------------|
| `/projects/[id]` | Kanban (спринт або весь проєкт, `?scope=`) |
| `/projects/[id]/list` | Список + SQL-фільтри + пагінація |
| `/projects/[id]/backlog` | Беклог і спринт, DnD між ними |
| `/projects/[id]/calendar` | Календар due dates (місяць, DnD дедлайну) |
| `/projects/[id]/gantt` | Гант |
| `/projects/[id]/jql` | JQL |
| `/projects/[id]/reports` | Burndown, velocity, облік часу |
| `/projects/[id]/dashboard` | Проєктний дашборд |
| `/projects/[id]/trash` | Кошик (Lead/Admin) |
| `/projects/[id]/settings` | Налаштування (Lead/Admin) |
| `/projects/[id]/issues/[issueId]` | Картка задачі (drawer з дошки через `?issue=`) |

### 7.3. Архівування проєкту

Lead/Admin може архівувати проєкт (soft-hide, без hard-delete у v1 UI).

## 8. Задачі (Issues)

### 8.1. Типи

`epic` | `story` | `task` | `bug` | `subtask`

### 8.2. Поля задачі

1. Ключ `PROJECT-N` (автоінкремент у межах проєкту).
2. Заголовок, опис (Markdown-текст).
3. Тип, статус, пріоритет (`highest`…`lowest`).
4. Виконавці (multi-assignee) і репортер.
5. Parent / Epic / Sprint.
6. Story points.
7. Original estimate / Remaining estimate (секунди).
8. Due date.
9. Labels (мітки).
10. Custom fields проєкту.
11. Rank (порядок на дошці/backlog).

### 8.3. Операції з задачами

| № | Функція | Хто |
|---|---------|-----|
| 1 | Створити задачу (з дошки/списку/backlog) | Member+ |
| 2 | Редагувати поля задачі | Member+ |
| 3 | Перемістити між статусами (DnD / форма) | Member+ |
| 4 | Призначити в спринт / прибрати в backlog | Member+ |
| 5 | Додати/змінити labels | Member+ |
| 6 | Зберегти значення custom fields | Member+ |
| 7 | Стежити / не стежити (watchers) | Viewer+ |
| 8 | Додати звʼязок (`blocks` / `relates` / `duplicates`) | Member+ |
| 9 | Залоговати час (work log, хвилини) | Member+ |
| 10 | Завантажити вкладення (≤ 25 МБ) | Member+ (і comment-доступ для upload у поточній реалізації через edit/comment path) |
| 11 | Завантажити вкладення з авторизованого API | Viewer+ (доступ до проєкту) |
| 12 | Коментувати (підтримка `@login` згадок з автодоповненням) | Viewer+ |
| 13 | Soft-delete в кошик | Member+ |
| 14 | Відновити / purge з кошика | Lead/Admin |

### 8.4. Сторінка задачі

Показує:
1. Форму редагування основних полів.
2. Коментарі.
3. Історію змін (activity).
4. Вкладення (для зображень — превʼю + збільшений перегляд).
5. Звʼязки.
6. Work log.
7. Кнопку «Стежити».
8. Автодоповнення `@логін` у коментарі (стрілки / Enter / клік).

## 9. Вигляди дошки

### 9.1. Kanban (`/projects/[id]`)

1. Колонки = статуси проєкту.
2. Картки задач з ключем, назвою, пріоритетом, типом, виконавцем, SP.
3. Drag-and-drop між колонками (Member+).
4. Якщо є активний спринт — на дошці задачі цього спринту (+ epic).
5. Живі оновлення через SSE (`GET /api/events?projectId=`): події пишуться в SQLite (`app_events`), тому працюють і між процесами; запасний polling версії дошки ~30 с.
6. WIP-ліміт статусу (якщо заданий) — підказка перевищення.

### 9.2. Список (`/projects/[id]/list`)

1. Таблиця: ключ, назва, тип, статус, пріоритет, виконавець, дедлайн.
2. Фільтри: пошук, тип, статус, виконавець.
3. Збереження поточного набору фільтрів як named view (особистий / спільний).
4. Швидкі посилання на збережені views.

### 9.3. Backlog (`/projects/[id]/backlog`)

1. Список задач без спринту.
2. Кнопка «У спринт» (в активний).
3. Створення майбутнього спринту (Lead).
4. Старт спринту (лише один active на проєкт).
5. Завершення спринту з переносом незавершених у backlog або інший спринт.

### 9.4. Календар (`/projects/[id]/calendar`)

1. Сітка поточного місяця з задачами за `due_date` (без soft-deleted).
2. Навігація попередній / наступний місяць (`?ym=YYYY-MM`).
3. Клік по задачі відкриває drawer (`?issue=`).
4. Member+ може перетягнути задачу на інший день — змінюється due date.

## 10. Спринти

| Статус спринту | Опис |
|----------------|------|
| `future` | Запланований |
| `active` | Поточний (макс. 1) |
| `closed` | Завершений |

Поля: назва, мета, дати початку/кінця.

При старті спринту фіксується **committed** (SP і кількість задач). Щодня / при зміні задач пишеться знімок залишку (`sprint_snapshots`). При завершенні — **completed** для velocity.

## 11. Налаштування проєкту (`/projects/[id]/settings`)

Доступ: Lead / Admin.

1. **Учасники:** додати з роллю lead/member/viewer; прибрати.
2. **Команди проєкту:** привʼязати команду з роллю за замовчуванням.
3. **Статуси:** додати статус (назва + category: todo / in_progress / done).
4. **Custom fields:** text / number / select / date / user; для select — опції через кому.
5. **Експорт:** CSV живих issues (без кошика), колонка `assignees` (усі виконавці).

---

## 12. Проєктний дашборд (`/projects/[id]/dashboard`)

Усі лічильники **без soft-deleted** задач.

1. Усього задач / учасників.
2. Активний спринт і прогрес (done / total, %).
3. Розподіл по статусах.
4. Created vs Done за останні 14 днів.
5. Стрічка активності проєкту.

Окремо **Звіти** (`/projects/[id]/reports`): burndown активного/обраного спринту, velocity закритих спринтів, work log за період (сума по людях).

## 14. Адміністративні налаштування інстансу

### 14.1. Налаштування (`/admin/settings`)

1. Змінити назву додатку.
2. Показати час останнього бекапу.
3. Інформація про папку `data/`.

### 14.2. Бекапи (`/admin/backups`)

1. Створити ручний dump SQLite **і** знімок `data/uploads/` (`*.uploads/` поруч із `.db`).
2. Список бекапів (імʼя, розмір БД, розмір файлів, дата).
3. Завантажити файл `.db` (знімок файлів лишається на сервері для restore).
4. Відновити з бекапу: перезапис БД; якщо є знімок uploads — він теж замінюється.
5. Автобекап ~раз на добу під час роботи додатку (`maybeAutoBackup`); зберігається 7 автокопій.
6. CLI: `npm run backup`.
7. Події create/restore пишуться в аудит.

### 14.4. Аудит (`/admin/audit`) — лише Admin

1. Таблиця останніх подій: вхід / невдалий вхід / блокування / бекап.
2. Поля: час, логін, IP, деталі.
3. Записи старіші за 365 днів прибирає фон.

### 14.3. Експорт

1. CSV живих issues проєкту: `GET /api/export/[projectId]` (колонка `assignees`).
2. Вкладення: `GET /api/attachments/[id]` (з перевіркою доступу).
3. Версія дошки: `GET /api/board-version/[projectId]`.

## 16. Технічні нефункціональні вимоги (реалізовані)

1. SQLite у режимі WAL, foreign keys ON.
2. Серверна перевірка прав на кожній мутації.
3. Вкладення не віддаються публічно без авторизації.
4. Ліміт upload через Server Actions: до 30 МБ body (файл ≤ 25 МБ).
5. Локалізація дат: `uk-UA`.
6. LAN: bind на `0.0.0.0`.
7. Ліміт логіну 5/15 хв; аудит входів.
8. Soft-delete 30 днів, потім hard-delete **разом із файлами** вкладень.
9. SSE-події в SQLite (`app_events`), TTL ~2 год.
10. HTTPS у LAN — через reverse proxy (Caddy/nginx); інстанс сам слухає HTTP.

## 17. Послідовний сценарій «день команди» (end-to-end)

1. Admin відкриває інстанс → setup (один раз) → створює користувачів і команди.
2. Admin створює проєкт → додає учасників/команди → за потреби статуси та custom fields.
3. Lead створює спринт → стартує його.
4. Member створює задачі в backlog → переносить у спринт.
5. Команда працює на Kanban (DnD статусів), коментує, додає файли, логує час.
6. Viewer переглядає прогрес і залишає коментарі.
7. Користувачі бачать сповіщення про призначення/зміни.
8. Lead завершує спринт; Admin робить бекап / експорт CSV.

## 19. Розширення (реалізовано)

1. **Multi-assignee** — `issue_assignees`, UI multi-select, фільтри/борда/нотифікації.
2. **Swimlanes** — на Kanban: Немає / Виконавець / Epic.
3. **JQL** — практичний піднабір на `/projects/[id]/jql`.
4. **Gantt** — Timeline + Dependencies на `/projects/[id]/gantt`.
5. **LDAP bind** — опційно в Адмін → Налаштування; локальний логін лишається.
6. **PWA** — manifest + service worker.
7. **Expo mobile** — клієнт у `mobile/` + REST (`/api/auth/login`, `/api/projects`, …).

## 20. Повний набір розширень (реалізовано)

1. **OIDC SSO** — `/api/auth/oidc/start` + callback; налаштування в Адмін.
2. **JQL+** — reporter, parent, epic, category, relative dates (`-7d`, `7d`, `now`).
3. **Gantt drag** — перетягування смуг і resize due date.
4. **Email (SMTP) + Telegram** — канали з Адмін; chat id у Профілі.
5. **Workflow rules** — require assignee/due, block open blockers, role gate.

## 21. Мобільні вкладення та push (реалізовано)

1. **Upload вкладень з телефону** — `POST /api/projects/:id/issues/:issueId/attachments` (multipart, поле `file`); у Expo — DocumentPicker.
2. **Завантаження вкладення** — `GET /api/attachments/:id` приймає cookie-сесію або Bearer API-токен; мобільний клієнт відкриває через FileSystem + Share.
3. **Push-токени** — таблиця `push_tokens`; `POST/DELETE /api/push/register`.
4. **Доставка** — `notifyUser` → email / Telegram / Expo Push (ExponentPushToken).

## 22. Gap-fix v1.1 (послідовність закриття дірок)

Реалізовано в такому порядку (залежності зверху вниз):

1. **Коректність даних.** Усі живі вибірки issues фільтрують `deleted_at IS NULL`: особистий дашборд, проєктний дашборд, open-counts на списку проєктів, due-soon, CSV, підзадачі, rank. CSV бере імена з `issue_assignees`.
2. **Файли при purge.** Hard-delete (кнопка в кошику і job через 30 днів) знімає файли з `data/uploads/` до `DELETE FROM issues`.
3. **Бекап вкладень.** `createBackup` копіює uploads у `dashboard-… .uploads/`; restore підміняє і БД, і файли, якщо знімок є.
4. **Ліміт логіну + аудит.** 5 невдач IP+логін / 15 хв → 15 хв паузи. Події на `/admin/audit`. Те саме для cookie-логіну, REST `/api/auth/login` і OIDC.
5. **Календар.** `?ym=`, prev/next, drawer, DnD due date (Member+).
6. **Кошик.** Діалог підтвердження перед «Видалити назавжди». Restore/purge — Lead/Admin.
7. **Згадки.** Випадаючий список по `@` зі стрілками/Enter; вставляє `@login`.
8. **Превʼю зображень.** Thumbnail + lightbox; `GET /api/attachments/:id?inline=1` віддає `Content-Disposition: inline` для `image/*`.
9. **Звіти.** `/projects/[id]/reports` — burndown (знімки SP), velocity закритих спринтів, work log за період (без задач із кошика).
10. **SSE між процесами.** `emitAppEvent` пише рядок у `app_events`; `/api/events` поллить таблицю кожні ~1.5 с (не лише in-memory EventEmitter).
11. **Гігієна.** Прибрано мертві HTML/сесії з кореня; `.gitignore` для `cookies.txt` / `session.id`; HTTPS описано в README як Caddy/nginx перед Next.
